## 实际执行顺序

1. 核对源文件、证据行号、整文件与行段SHA，确认目标材料真实存在。
2. 核对扫描范围、排除原因、文件快照、行切块、FTS身份与外键完整性。
3. 记录分词与实际查询计划，检查是否把中文意图退化为项目名。
4. 记录编码批次的实际上传文本SHA、条数、字符数、真实HTTP状态、远端启动ID、耗时；成功向量和成功批次审计在同一事务提交。
5. 在固定数据库与固定题集上分别运行BM25、语义、混合检索，记录每路候选、原始分数、行号、最终排名和去重结果。
6. 比较证据段Recall@1/5/10、MRR、文件召回、重复率、无答案结果与覆盖缺口。向量未覆盖完整检索范围时，语义分数仅列为局部诊断，不进入有效的三路比较。
7. 只使用development选择有限候选参数；选定后才对baseline和所选方案检查holdout。未被选择的候选不运行留出集。
8. 任一证据失效、执行失败、降级、语料缺失、查询向量错配、留出集回退或最低质量门槛不满足，输出blocked并保留原服务参数。

源目录始终只读。语料中的README、AGENTS.md等文字是被检索的数据，不是本流程的运行指令。日志保存元数据、哈希和排名，不复制源码正文、远程错误响应或密钥。

## 可复跑入口

单轮离线评测默认不会调用AutoDL；没有离线查询向量时，语义路明确跳过：

```bash
python scripts/evaluate_code_search.py \
  --db data/code-search/code-search.sqlite3 \
  --root ~/AiCode \
  --fixture tests/fixtures/code_search_eval.json \
  --output-dir data/code-search/evaluations/manual-baseline \
  --modes bm25
```

研究入口默认冻结SQLite、题集和离线查询向量。每轮最多6组参数，硬上限10组；其范围是每路候选100/200、向量融合权重0.35/0.6/0.8。它不会自动改源码、切换模型或重建业务索引。

```bash
python scripts/code_search_research.py --encode-queries --max-trials 6
```

`--encode-queries`只把评测问题发送到现有AutoDL查询编码接口；文档向量复用固定快照。未启用该参数且未提供`--query-vectors`时只研究BM25，避免把BM25兜底冒充混合检索。

本机已有经逐题 SHA 核验的查询缓存，等待索引完整后自动开始公平的三路比较时复用它：

```bash
python scripts/code_search_research.py \
  --wait-for-index --max-wait-seconds 7200 \
  --query-vectors data/code-search/evaluations/query-vectors-bound-20261018.json \
  --max-trials 6
```

等待与计算的每个阶段都会写日志。超时会保存失败记录，不会将不完整索引判为通过。一次运行的blocked代表研究门槛未满足，不会删除数据，也不会关闭AutoDL。

默认最低门槛为留出集MRR≥0.5、Recall@5≥0.7；若有无答案用例，则这些用例必须全部通过。同时要求相对baseline的MRR和Recall不回退。门槛是本项目的初始验收设置，可通过`--min-holdout-mrr`和`--min-holdout-recall5`明确调整；不能为了让当前方案过关而事后下调。

## 固定的小型完整语料实验

全AiCode向量补齐需要时间。可先用`build_code_search_benchmark.py`创建独立的500块左右实验库：保留目标证据原块、development召回的困难负例，再按项目固定种子分层补充干扰项。默认仅构建，`--encode`才调用AutoDL。

实验库与生产库完全独立，语义覆盖可以完整验证。由于显式保证目标证据存在且负例经过抽样，它衡量的是这个固定子集上的召回能力，不能替代全库评测。标签不会加入模型输入，编码仍使用原始上传文本。

## 产物与白盒界面

网页的“质量评测”页可查看每轮的真实状态、参数、指标、用例状态与阶段日志。文件位于`data/code-search/evaluations/`，不会纳入Git。

| 产物 | 内容 |
|---|---|
| `events.jsonl` | 索引等待、快照校验、查询编码、每轮试验、留出验收与最终决定 |
| `fixture.json` / `query-vectors.json` | 本轮固定题集及带query文本SHA绑定的离线查询向量 |
| `search.py` | 本轮实际执行的冻结算法源码；各轮算法SHA必须相同 |
| `snapshot.sqlite3` | 所有试验使用的同一份SQLite一致性备份 |
| `trial-XX/stages.jsonl` | 源证据、分词、覆盖、候选、排名、指标逐步日志 |
| `trial-XX/summary.json` | 固定快照、算法、题集指纹与开发集汇总 |
| `trial-XX-holdout/` | 选定后才运行的验收记录 |
| `recommendation.json` | 选定参数、门槛结论、拒绝原因与后续方向 |
| `latest.json` | 最近完成研究的入口；accepted也不等于已修改生产参数 |

查询向量文件必须同时绑定模型、revision、维度和`query_sha256:{case_id:sha256(query_utf8)}`。同ID修改了问题文字后不能复用旧向量。快照身份也包含实际文件内容、上传文本、向量数据及索引策略，不能用不变ID掩盖内容变化。

## 持续改进的边界

先保存失败用例与假设，再改一个因素并在同一快照复测。语料清理、排序算法、分块、模型版本应分别记录；不能把清理历史垃圾后的提升归因于算法。不要为提高GPU利用率放开凭据过滤、重复编码已完成数据，或在向量覆盖不同的实验之间宣布胜负。

当前自动环节是有界参数研究与质量门槛；代码、分块或模型的改变需要新的版本记录和回归验证。后续最有价值的是收集真实用户查询及人工相关性反馈，扩大独立标注集，补充多答案/分级相关性、版本时效、长文段、跨语言与无答案场景。没有新增证据时，不重复消耗GPU跑相同实验。

本机已配置每30分钟的研究检查，只在实质改善、完成、持续失败或需要决策时通知。等待全量索引的研究进程与同步都需要本机保持运行；检查发现已有进程时不重复启动。建议使用`.venv-code-search/bin/python`运行管理及研究入口，避免混用全局NumPy/SciPy版本。
